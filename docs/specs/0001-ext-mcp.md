# searxng-mcp-ext:内嵌 HTTP MCP 的 SearXNG 扩展镜像

## 问题陈述

想要给 AI 助手接上搜索能力的人,今天必须自己拼装至少三样东西:一个 SearXNG 实例、一个 MCP 服务器、以及把两者连起来的配置。每一步都有各自的坑——SearXNG 的 JSON API 默认关闭、中文搜索引擎默认禁用、MCP 服务器要么以 stdio 方式被客户端 `docker run` 拉起(每台机器都要装容器运行时),要么需要单独部署并配置网络。

结果是一个对"只想让 agent 能搜网页"的人来说过重、对"想搜中文"的人来说默认不可用的组合。

## 解决方案

一个预构建的容器镜像,把「搜索后端」和「MCP 接口」合成一件事:

- 基于官方 SearXNG 镜像(固定版本 tag)构建,注入中文搜索引擎与付费兜底引擎
- 在**同一个进程内**新增一个 HTTP MCP 端点 `/ext/mcp`,暴露单个工具 `web_search`
- 镜像由 CI 自动构建并发布到 GHCR;**使用者只需两个文件**(构建定义与编排定义)即可部署
- AI 客户端只需填写一个 URL,**不需要安装任何东西、不需要 `docker run` 参数、不需要 stdio 配置**

对使用者而言:得到一个"填个地址就能搜"的服务,且默认就对中文查询友好。

## 实现决策

### 架构:同进程内嵌

MCP 端点与 SearXNG 运行在**同一个容器、同一个进程**内,并把这一点作为项目的核心主张——部署者只需要管理一个单元。这**不是**社区推荐的形态(SearXNG 维护者在多个 issue 中明确表示 MCP 集成应作为独立项目通过 API 交互),项目有意接受这一取舍并在 ADR 中记录理由。

容器内只有一个服务进程:应用服务器以 **ASGI 接口**启动一个组合应用,该应用把两个挂载点绑在一起——MCP 端点挂在 `/ext/mcp`,SearXNG 原有的 WSGI 应用挂在根路径(通过 WSGI-to-ASGI 适配中间件原样包裹)。**SearXNG 的源码不做任何修改。**

这替代了早期考虑的"在 Flask 内手写传输层"方案,理由是官方 MCP SDK 已提供成熟的传输实现(会话管理、SSE 帧、初始化握手),手写等于重新实现一遍协议中最容易出兼容问题的部分。

### MCP 工具契约

端点暴露**单个**工具 `web_search`,参数如下:

- `query`(字符串,必填)—— 搜索词
- `count`(数字,可选,默认 20,上限 50)—— 返回结果条数。注意:**SearXNG 本身不接受该参数**,它只用于服务端截断
- `time_range`(可选,枚举 `day` / `week` / `month` / `year`)—— 时间范围
- `categories`(可选,枚举 `general` / `it` / `repos` / `code` / `videos` / `news` / `images`)—— **固定枚举**,取值由本镜像的引擎清单唯一决定

返回同时提供两种形态:

- 人类可读的 Markdown 文本,格式为逐条的 `序号. [标题](URL)` 加摘要正文
- 结构化字段,即领域词汇中的**搜索结果协议三元组** `{url, title, content}`

当某条结果需要用浏览器自动化才能读取时(目前唯一已知的情况是 ChinaSo 的加密跳转链接),该条结果额外携带一个提示字段,标记读取模式为浏览器。字段名可调整,语义不可变:**它出现在工具返回值描述中,让 agent 知道这条 URL 不能通过普通 HTTP 抓取**。字段只在需要非默认模式时出现,不逐条冗余携带。

**ChinaSo 的处理**:该引擎返回的 URL 是加密跳转链接,既不可本地解码,也不满足搜索结果协议中"同一网址对应同一内容"的稳定性假设。项目**有意保留该引擎**,通过上述提示字段把解析责任交给下游的抓取工具,而不是在搜索路径上做同步解析(上游 issue #4694 记录了解析会超时的实测结果)。

### 传输与协议

只实现 **Streamable HTTP** 传输。不提供 stdio,不提供已废弃的 HTTP+SSE 双端点传输。Streamable HTTP 按现行规范实现,包括其在流式场景下使用 `text/event-stream` 的能力。

### 引擎清单

镜像内启用以下引擎,并**通过白名单机制只保留这些**:

```
general : google, bing, baidu, duckduckgo, 360search, sogou, quark, braveapi, bocha
it      : github, github code, baidu kaifa
repos   : github
code    : github code
videos  : bilibili, iqiyi, acfun, 360search videos, sogou videos
news    : sogou_wechat
images  : baidu images, quark images, sogou images
```

包 API key 的引擎(`braveapi`、`github code`)在未提供密钥时**优雅降级**而非报错——该引擎不启用,不影响其余引擎的正常聚合。

博查引擎(`bocha`)在发起 API 调用时**默认拉满 50 条结果**,以最大化单次付费调用的信息量;这与工具层的 `count` 参数是两个独立的量,后者只控制返回给 agent 的条数。

### 密钥配置

博查 API key 通过**环境变量**注入。这一决定是在验证后确定的:引擎的可访问请求参数类型中**不包含任何入站 HTTP 请求头字段**,因此"客户端通过 header 传递密钥"的方案在技术上无法实现。

### 构建与分发

**交付物是两个文件:构建定义(Dockerfile)与编排定义(docker-compose.yml)。**

- **构建由 CI 承担**:代码推送到仓库即触发自动构建,产物推送到 GHCR。使用者与部署者都**不需要本地构建**
- **编排指向预构建镜像**:编排文件引用 GHCR 上的镜像(`image:` 形式),**不含 `build:` 段**。使用者拿到编排文件后直接启动即可,不需要容器构建工具链
- 基础镜像:**固定版本 tag**(与参考项目保持一致的具体版本),不做 `latest` 跟随
- 发布目标:**GHCR**,与 GitHub 仓库同源,推送凭据复用现有凭据
- 镜像需要额外安装官方 MCP SDK。经验证,该 SDK 的依赖与 SearXNG 的依赖**无冲突**(SearXNG 使用 `curl_cffi` 而非 `httpx`,且不使用 pydantic,二者在 `typing-extensions` 上版本范围兼容)

### 引擎数据传递的已废弃路径

参考实现中存在一条通过 `engine_data` 机制向博查引擎传递时间范围的路径。**该路径已被移出设计**,原因有三:格式不符合上游解析规则(上游要求连字符分隔的三段式键名,参考实现用了方括号形式,会导致请求解析异常);博查引擎的引擎侧实现**已经内置**了时间范围到自身格式的映射,外部重复传递是冗余的;上游的时间范围参数只有四个枚举值,参考实现试图传递的日期区间在上游根本无法产生。

## 测试决策

### 缝

**唯一缝:容器边界。** 本项目的交付物是一个镜像,不存在可供单测的库级接口,因此所有行为都在容器边界上可观察。测试通过启动容器、以真实 MCP 客户端连接端点、断言外部可见行为来进行。

### 好的测试

只断言外部可见行为:**从客户端发出的请求能得到什么**。不断言内部实现——不检查容器内有几个进程、不检查用的是哪个 ASGI 中间件、不检查引擎以何种方式被加载。重构内部结构不应导致任何测试失败。

### 覆盖点

1. MCP 工具清单包含 `web_search`
2. 调用 `web_search` 返回文本结果与结构化三元组结果
3. `count`、`time_range`、`categories` 参数各自生效
4. 空结果返回可读的空态说明而非错误
5. SearXNG 原生路径在组合应用下未回归:根路径返回界面、JSON 搜索端点可用、静态资源可加载
6. 引擎清单生效:实例的引擎/分类枚举与配置一致
7. 未配置博查密钥时服务正常启动且其余引擎工作
8. 需要浏览器读取的结果携带对应的提示字段
9. 编排文件引用的镜像可直接拉取启动,不需要构建步骤

### 已知需要实测确认的风险

以下三项在实现前需通过实跑验证,**任一项失败都会回改设计**:

- 组合应用下 SearXNG 的静态资源、图片代理等依赖 WSGI 环境的特性是否正常
- 工具在容器内通过 HTTP 自调用自身搜索端点时,在应用服务器阻塞线程数有限的前提下,**并发下是否会出现自调自锁**
- 官方 MCP SDK 安装进上游镜像的 Python 虚拟环境的方式(该环境属主为非 root 用户)

## 不在范围内

- **网页抓取与文档解析**(参考项目中的 URL 读取与文件解析能力)。这些属于另一个工具层的职责,本项目的提示字段只是为该层提供输入
- **反向代理与限流**。部署者自行提供;本项目不内置入口层
- **端点鉴权**。有意不做,交由外部网关
- **stdio 传输**与**已废弃的 HTTP+SSE 双端点传输**
- **域名过滤参数**(参考实现中的 `include`)。上游支持 `site:` 查询语法,模型可直接使用。排除式过滤(`exclude`)留待后续
- **动态分类枚举**。当前采用固定枚举,因为本镜像的引擎清单是封闭的
- **多租户密钥隔离**。当前密钥由部署者统一配置
- **自动跟随上游 SearXNG 新版本**(定时探测并开 PR)。固定版本 tag 由人工 bump。注意这与"CI 自动构建本镜像"是两件事——**后者在范围内**

## 其他说明

- **许可证**:AGPL-3.0-or-later,与上游一致。本项目分发包含上游代码的镜像,且通过网络提供服务,处于 AGPL 网络条款覆盖范围内
- **与上游的关系**:非官方派生项目。README 需明确声明不隶属于 SearXNG 项目,且不使用其官方标识
